## 1. Course builder — level, language, cover & lesson uploads

`45312d3` · 12:18 · 6 files, +245/−1

The builder needed three capabilities the API did not have.

**New fields on `Course`** (migration `0046`, later renumbered to `0047`):

```python
level    = CharField(max_length=20, choices=LEVEL_CHOICES, blank=True, default='')
language = CharField(max_length=50, blank=True, default='English')
```

Both are `blank=True` with defaults, so existing rows are untouched and a client
that omits them still creates successfully. `level` is deliberately optional —
an instructor who does not pick one gets no level row on the card rather than a
wrong one.

**Asset upload** — `POST /courses/{id}/assets/`

- owner or admin only
- MIME allowlist per kind
- **8 MB** cap for a cover, **500 MB** for a lesson file
- responds `{url, path, kind}` with an absolute URL
- covers reuse the lesson upload path rather than adding a second one

**Thumbnail round-trip.** `thumbnail_url` now stores a storage *name* instead of
an absolute URL: `to_representation` resolves it through `media_src()`, and
`validate_thumbnail_url` strips our own `/media/` prefix back off before saving.
This exists because the client PATCHes back the URL the server just echoed, and
an absolute URL in the column breaks the moment the dev box changes IP — which
on this machine it does routinely.

**Enrolment read** — `GET /courses/{id}/enrollment/`

- 200 with the student's own enrolment
- 404 when there is none
- 401 anonymous

This is the only way to distinguish "paid up" from "started paying and stopped":
`POST enroll/` refuses a second call for a `pending_payment` row exactly as it
does for an active one. The client needs that distinction before it opens a
player whose every lesson would answer 403.

Verified: `test_course_batch2` (21 OK), `test_payments` (36 OK alongside).

## 4. Payments — four separate defects, all found by live probing

These were not test failures. Each was found by exercising the running server,
and two of them had passing tests that covered the mapping but not the
consequence.

### 4.1 A status read killed payments still in flight
`51e8ca3` · 12:18 · 4 files, +44/−4

eSewa answers `NOT_FOUND` for a `transaction_uuid` it has never seen — which is
*every* payment between `initiate` and the student submitting the form.
`ESEWA_STATUS_MAP` mapped that to `failed`, and `refresh_payment` returns early
for any row that is not `initiated`. So the **first status poll marked the
payment failed permanently**: a payment completed two seconds later could never
be confirmed, and the student would have paid for a course that stayed locked.

Fix: `refresh_payment(payment_id, *, settle_missing=False)` leaves the row
`initiated` on `NOT_FOUND` unless the caller explicitly asks for a verdict. Only
the two places where "not found" has had time to mean "never happened" ask — the
`recheck_payments` sweeper (5-minute default age) and an admin recheck. Every
client-triggered read is a read.

An abandoned payment therefore stays `initiated` until the sweeper runs. That is
the honest state: the gateway has not said anything, and only a `successful` row
unlocks a course.

`test_verify_ignores_client_claimed_success` now expects `initiated` rather than
`failed`; the property it guards — the client's own claim is never trusted — is
unchanged. A new test polls three times against `NOT_FOUND`, asserts the row
survives, then confirms the same payment can still settle `successful`.

### 4.2 The gateway call held a row lock
`0d986a6` · 13:02 · 3 files, +107/−8

The checkout sheet polls `GET /payments/{id}/` every two seconds while the
gateway's return view refreshes the same row. Both went through
`refresh_payment`, which opened `transaction.atomic()`, called eSewa **inside
it** (15-second timeout) and only then wrote. Every poll held a row lock for the
length of an HTTP round trip.

On the dev SQLite database that is not a slowdown, it is a failure: **15 of 18
concurrent requests answered 500** with `OperationalError: database is locked`,
and because the return view is a plain browser page the student saw a Django
error page mid-payment.

New shape: **read → ask the gateway → lock → re-check → apply.** The re-check
under the lock is what keeps "apply once" true when two polls race, and it is
the only guard that works on SQLite, where `select_for_update()` is silently a
no-op — the backend has no `SELECT … FOR UPDATE`. The previous docstring's
concurrency claim was therefore not true there.

`config/settings.py` gains, for SQLite only:

- **20-second busy timeout** — the default 5 s is shorter than the overlap the
  app creates by design
- **IMMEDIATE transactions** — `DEFERRED`'s late lock upgrade is the case SQLite
  cannot resolve by waiting

After: **60 of 60 concurrent requests, no locks.** Two tests pin the behaviour —
the gateway call is measured outside any transaction, and a settled payment is
not asked about twice.

### 4.3 The deep link back to the app returned 400
`9b5caf9` · 12:27 · 2 files, +59/−1

`_finish` redirected to `skillsikka://payment?…` using Django's `redirect()`,
which trusts only `http`, `https` and `ftp` and raises `DisallowedRedirect` for
anything else. The student paid, eSewa sent them back, and they landed on a
**400** — the deep link the whole checkout sheet waits on never fired.

The branch was invisible while `PAYMENT_APP_RETURN_URL` is empty, which is why
it passed review: every existing test ran with the setting blank and asserted
the relative result page.

Fix: `_AppRedirect` widens `allowed_schemes` by one. An https universal link
still passes the default check, so nothing that worked before is loosened.

### 4.4 A busy row produced an error page for someone who had already paid
`a3c3685` · 13:04 · 2 files, +31/−1

The gateway return view is a plain browser page; its whole job is to hand the
browser back to the app. A write collision there rendered a Django error page in
front of someone whose money may already have moved.

`_refresh_quietly` now also swallows `OperationalError`, logs it, and returns the
payment untouched — the row keeps `initiated`, and the app's two-second poll
settles it moments later. The error still surfaces where it is actionable:
`GET /payments/{id}/` is an API call, not a page.

## 5. `mark_paid` — a sandbox escape hatch

`222040f` · 13:23 · 3 files, +215/−28

eSewa's test environment is unusable when its reCAPTCHA Enterprise quota is
exhausted: the widget cannot issue a token, so every login fails with
"Invalid eSewa ID or password" even with the published test account. Everything
*after* the payment — enrolment goes active, the player opens, My Learning picks
it up — was untestable as a result.

```
manage.py mark_paid <id> [--status] [--reference]
```

- settles a payment without the gateway
- **refuses to run with `PAYMENT_MODE=live`** — a command that marks payments
  paid must never sit next to real money

To make the test meaningful, the apply step moved out of `refresh_payment` into
**`settle_payment`**, which the command calls too. Both paths therefore activate
the enrolment and write the notification through the same code; a separate
implementation would have tested nothing. `refresh_payment` keeps its shape:
read, ask the gateway outside the transaction, then settle under the lock with
the re-check that makes it apply once.

New test module `core/test_mark_paid.py` (94 lines).

## 6. Regression caught: a duplicate `to_representation`

`eb81301` · 12:43 · 1 file, +15/−13

`CourseSerializer` already had a `to_representation` merging the bootcamp
profile, the instructor roster and the resource/discussion counts into the
response. The cover-image work added a **second** `to_representation` further
down the class body — and a class body keeps only the last definition of a name,
so the new one silently replaced the old one.

The diff looked purely additive, so nothing flagged it. The symptom: every
bootcamp response lost `venue_name`, `days`, `starts_on`, `ends_on`, `status`,
`instructors` and the counts. `core.test_bootcamps` went from **68 passing to 4
failing**. Nothing in the payment work noticed, because no payment path reads a
bootcamp.

The cover resolution now runs inside the single `to_representation`, after the
bootcamp block.
